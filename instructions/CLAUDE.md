# Mirket working instructions

- On each request, identify and use the smallest relevant set of skills from the active **Mirket** plugin before substantive work. Apply **Execute** throughout: take the simplest complete path and report what matters. Use **Author** for general writing and issue triage, **Market** for marketing messaging and claims, and **Ship** for product requirements. If Mirket is unavailable, say so, follow these defaults, and continue authorized work.
- When it is unclear which skill should own the result, consult the active Mirket plugin's `skills/execute/references/Routing.md`. Add support at the start or during work when it can answer a distinct question, fill an evidence gap, or guide a decision.
- Use **Audit** for security and privacy review and **Architect** for design-time threat modeling. The implementer owns authorized hardening. The task owner follows `skills/execute/references/VersionedDistribution.md` for release preparation and authorized publication. Use **Migrate** for persistent-state transitions and **Deploy** for environment rollout, service health, incidents, and recovery. Honor existing authority; preparation, publication and production activation are separate scopes.
- Read the project's instructions and current state before changing it. Respect existing conventions and user changes. Prefer the smallest complete solution; challenge a poor tool fit with evidence and a better option.
- Plan substantial implementation with **Plan**. Ground decisions in evidence, keep product and business choices with the human, and record the agreed outcome and checks. Keep routine work direct and read-only reviews free of execution plans.
- Keep agent-created temporary artifacts in `.work/temp/<task>/` at the current Git worktree root or selected non-Git project root. Set tool output paths there before generating scratch scripts, logs, renders or test output. Use designated paths for deliverables.
- Before the first project write in a Git project, automatically check and fix the root `.gitignore`. Ignore only `.work/temp/`, `.work/recover/`, `.work/stashes/` and `.work/routines/` within the workspace. Keep reusable device-specific project procedures in `.work/routines/`. Keep `.work/`, its plans, briefs and decisions visible to Git. Use the project's existing architecture decision directory when present, otherwise use `.work/decisions/`. Follow the active plugin's `skills/execute/references/Workspace.md` for verification and record numbering.
- Use focused checks and required project checks. For every visual check, follow Design’s full-surface capture standard in `skills/design/references/tools/Screenshot.md`. Keep visual acceptance open until the full high-resolution original has been verified and inspected. Apply **Clean** before delivery and before committing; preserve unrelated work and important records.
- Lead with the result, cite useful evidence, and state material limits. Report only checks and actions that actually happened.
