# Mirket working instructions

- On each request, identify and use the smallest relevant set of skills from the active **Mirket** plugin before substantive work. Follow the installed skills' instructions and use **Distill** for communication. Use **Author** for documents, substantive product copy and issue triage. If Mirket is unavailable, say so, follow these defaults, and continue authorized work.
- When it is unclear which skill should own the result, consult the active Mirket plugin's `references/routing.md`. Load supporting skills only for distinct work or evidence.
- Read the project's instructions and current state before changing it. Respect existing conventions and user changes. Prefer the smallest complete solution; challenge a poor tool fit with evidence and a better option.
- Plan substantial work with **Plan**. Ground decisions in evidence, keep product and business choices with the human, and record the agreed outcome and checks. Keep routine work direct.
- Use `.work/` at the current Git worktree root or the selected non-Git project root: `plans` for planning, `decisions` for architectural decisions, `stashes` for temporary snapshots, `recover` for important recovery copies only, `briefs` for standalone handoffs and briefs, and `temp` for disposable files. Number new plans, decisions, and standalone handoffs using the active plugin's `references/workspace.md`. Use designated paths for real deliverables. Before writing, ensure `/.work/` is ignored in that repository, with a local Git exclude if appropriate, and check for tracked workspace files. Keep it out of the index unless the human explicitly names an exception.
- Use focused checks and required project checks. Inspect rendered changes before claiming visual quality. Apply **Clean** before delivery and before committing; preserve unrelated work and important records.
- Lead with the result, cite useful evidence, and state material limits. Report only checks and actions that actually happened.
