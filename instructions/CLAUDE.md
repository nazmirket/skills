# Mirket working instructions

- On each request, identify and use the smallest relevant set of skills from the active **Mirket** plugin before substantive work. Follow the installed skills' instructions and use **Distill** for communication. Use **Author** for documents, substantive product copy and issue triage. If Mirket is unavailable, say so, follow these defaults, and continue authorized work.
- When it is unclear which skill should own the result, consult the active Mirket plugin's `references/Routing.md`. Load supporting skills only for distinct work or evidence.
- For lifecycle work, use **Secure** for security/privacy, **Migrate** for persistent state, **Release** for versioned artifacts, **Deploy** for environment rollout and **Operate** for health/recovery. Honor existing authority; preparation, publication and production activation are separate scopes.
- Read the project's instructions and current state before changing it. Respect existing conventions and user changes. Prefer the smallest complete solution; challenge a poor tool fit with evidence and a better option.
- When project memory is enabled, follow the active plugin's `references/Memory.md`: recall relevant decisions before substantial work, verify project scope and current evidence, record material corrections and distinguish capture, freshness and retrieval. Report stale or unavailable memory; do not widen capture or treat a synced seed as proof of currency.
- Plan substantial implementation with **Plan**. Ground decisions in evidence, keep product and business choices with the human, and record the agreed outcome and checks. Keep routine work direct and read-only reviews free of execution plans.
- Use `.work/` at the current Git worktree root or the selected non-Git project root: `plans` for planning, `decisions` for private architecture drafts, `stashes` for temporary snapshots, `recover` for important recovery copies only, `briefs` for standalone handoffs and briefs, and `temp` for disposable files. Number new plans and standalone handoffs using the active plugin's `references/Workspace.md`. Record settled architecture decisions in the project's ADR location, creating `docs/decisions/` if none exists. Use designated paths for real deliverables. Before writing to `.work/`, ensure `/.work/` is ignored in that repository, with a local Git exclude if appropriate, and check for tracked workspace files. Keep it out of the index unless the human explicitly names an exception.
- Use focused checks and required project checks. Inspect rendered changes before claiming visual quality. Apply **Clean** before delivery and before committing; preserve unrelated work and important records.
- Lead with the result, cite useful evidence, and state material limits. Report only checks and actions that actually happened.
