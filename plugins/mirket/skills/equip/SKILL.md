# Equip

Call out the fork when the job needs a spoon. Be blunt about the choice and precise about its consequences. Aim the criticism at the tool or method, never at the person.

1. **Name the job.** State the desired result, what would prove it works, and constraints that matter: compatibility, permissions, cost, or a required project convention. Reuse what [Adapt](../adapt/SKILL.md) already established about the workflow.
2. **Trace where the method falls short.** Inspect the actual commands, inputs, handoffs, and output. Identify the first step where a needed capability is missing, the output loses information, or avoidable work repeats. Cite the failure, limitation, or observed cost. Distinguish a missing capability from one that exists but is disabled, misused, or broken. Use [Debug](../debug/SKILL.md) when a suitable method unexpectedly fails. If evidence is thin, run a small authorized check or say what is still unknown.
3. **Pick the smallest better fit.** First check whether a project tool, configuration, or simpler workflow already solves the problem. If something new is needed, state the missing capability before naming a tool. Use [Curate](../curate/SKILL.md) when comparing outside options and [Preflight](../preflight/SKILL.md) to check whether the chosen approach can run in the target environment. Compare the cost of switching with the cost of keeping the workaround. If the current method is a reasonable fit under the actual constraints, say so.
4. **Say it plainly.** Lead with the mismatch, then give the evidence, its consequence, and one concrete next step. For example: “A screenshot is a fork for this soup. It can show the checkout screen, but it can’t tell you whether you can finish checkout with a keyboard. Run the flow in a browser using the keyboard.” State what would confirm the alternative is better. Present the proposed change to the project's tool or workflow and ask the human before adopting it, even during otherwise authorized work. Continue independent work that does not depend on the switch while waiting.

**Done:** The human knows whether the current method fits, which capability or step is the real constraint, and what to try next. Do not switch the project's tool or workflow until the human agrees to the proposed change.
