# Equip fit scenarios

Use these cases to recognize the mechanism of a mismatch. Each situation is hypothetical; the recommendation depends on its stated constraints. Check real evidence before applying it to another project.

| Working choice | What to challenge and try | Evidence or reason to keep it |
| --- | --- | --- |
| **1. XLSX as a transport envelope.** Two unattended jobs exchange one flat table nightly; neither needs formulas, formatting, or multiple sheets. | Compare CSV with an explicit schema, encoding, and null convention. Consider JSON if the records are nested or the receiving contract calls for it. Compare actual file sizes instead of assuming which format is smaller. | Round-trip representative rows through both consumers, including IDs with leading zeros, dates, delimiters, and missing values. Keep XLSX when a consumer requires it or relies on workbook features. |
| **2. Binary floating point for a ledger.** Amounts are stored as floats and rounded for display; simple invoices look correct. | Challenge the underlying arithmetic. Use a suitable exact decimal representation, or integer minor units where the currency and calculations allow it. Obtain the applicable rounding and allocation rules before changing the representation. [PostgreSQL numeric types](https://www.postgresql.org/docs/current/datatype-numeric.html). | Test discounts, taxes, partial refunds, and reconciliation against independent expected totals. Reconcile existing records before a migration; changing the type cannot reconstruct precision already lost. |
| **3. An opinionated UI kit for a highly custom interface.** The screen works by overriding library internals and patching markup after upgrades. | Identify the work spent undoing the library's defaults. Compare a supported extension in the existing library with a lower-level primitive that provides the behavior without prescribing the appearance. [Radix Primitives](https://www.radix-ui.com/primitives/docs/overview/introduction) is an example to assess when it fits. | Pilot the hardest component. Compare customization effort and control, then exercise keyboard and focus behavior. Keep the current kit where its defaults fit; avoid rewriting unrelated components. |
| **4. Loading a whole dataset for a selective query.** A pandas script reads all columns of large Parquet files and filters to a few columns and rows. It finishes, but does work the result may not need. | First compare reading fewer columns and applying supported filters with the existing stack. If the job is mostly SQL filtering and aggregation, try querying the files directly with a tool such as DuckDB. [pandas scaling guidance](https://pandas.pydata.org/docs/user_guide/scale.html), [DuckDB Parquet support](https://duckdb.org/docs/stable/data/parquet/overview). | Compare equal results, peak memory, and elapsed time on the same representative data. Keep the tuned baseline if a new engine adds more operational cost than the measured gain warrants. |
| **5. An AST rewrite that discards source details.** A codemod produces correct Python, but the diff loses comments and alters formatting that must be preserved. | Choose a representation that retains source details. For Python, [LibCST](https://libcst.readthedocs.io/en/latest/) is an example; verify support for the project's syntax. | Try one representative file. Verify behavior and inspect the diff for changes beyond the intended edit. Keep an AST for analysis or for transformations where the source details do not matter. |
| **6. Replacing an ORM to fix excess queries.** An orders page renders, but it loads each order's customer in a separate query. The user wants a new ORM. | Check the loading strategy first. Try the existing ORM's supported eager-loading options for the relationship. [SQLAlchemy relationship loading](https://docs.sqlalchemy.org/en/20/orm/queryguide/relationships.html). | Compare query count and returned rows, including pagination and repeated customers. Adopt the smaller change if it fixes the query pattern without creating a new problem. |
| **7. Splitting CSV on commas.** A hand-written parser works on current exports, but the producer can emit quoted delimiters and multiline fields. | Use a standard CSV parser configured for the producer's dialect. [Python CSV handling](https://docs.python.org/3/library/csv.html). | Exercise a quoted comma, an escaped quote, and an embedded newline. A simple split is sufficient only if the input contract really excludes those cases. |
| **8. Click automation for a data export.** A daily browser job downloads files successfully, but layout updates require repairs. A supported API may expose the same data. | Check the API's authorized scope, filters, pagination, and rate limits. If it covers the job, pilot the API path on a small export. | Reconcile the exported records and fields with the UI. Keep browser automation for operations that require the UI or lack a supported equivalent. |
| **9. Similarity search for exact identity.** A vector search returns the correct SKU most of the time. | Use a keyed lookup for exact IDs with explicit normalization and a clear not-found result. Use semantic search where the input describes a product rather than identifying one. | Check close-looking IDs, ambiguous normalization, and unknown IDs. A search suggestion and a confirmed identity have different success criteria. |
| **10. A language model computes financial totals.** Its answers look plausible and pass a few spot checks. | Use a deterministic query or program for arithmetic with explicit input and rounding rules. A model can help explain the computed results. | Reconcile totals against known inputs and check missing or duplicate records. Test the calculation independently of the explanation. |
| **11. A server runtime for a static site.** A docs site runs an app server even though its pages can be built ahead of time. | Check for runtime needs such as authentication, request-time content, or redirects. If the deployable artifact is fully static, compare serving the export with the existing web server. | Verify routes, assets, navigation, caching, and real 404s. Keep a runtime where it provides required behavior that static hosting cannot replace. |
| **12. A workbook that serves the whole job.** People review formulas, annotate sheets, and approve an XLSX workbook. An automated consumer would prefer JSON. | Keep the workbook for review. Consider a separate structured export if automation needs one, with a clear source of truth. | Verify the export matches the approved values and preserves identifiers. The human review and approval steps are part of fit. |
| **13. A faster library with an unjustified migration.** The supported incumbent passes the required cases and runs a small weekly job. A competitor could run it faster, but the replacement changes several interfaces. | Compare the value of the improvement with compatibility work, migration risk, and future maintenance. Recommend keeping the incumbent if the benefit is immaterial. | Revisit if workload, latency requirements, or support changes enough to tip the decision. Record the threshold when known. |

For a new task with no chosen tool, start from the job rather than the catalog. For example, to publish a docs site, find out what must be served at request time and check the project's existing build and hosting before selecting a stack.

When a needed capability is absent, separate the proof from the workaround. An HTTP request can establish that checkout responds, but it cannot establish keyboard operation. Verify browser availability with [Preflight](../../preflight/SKILL.md), explain what obtaining access requires, and exercise the actual interaction once the capability is available. Likewise, when an already chosen test runner needs setup, check the supported version and installation scope, honor authorization, and prove readiness by running a representative project test.
