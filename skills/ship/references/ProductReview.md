# Product review

Compare the outcome observed after release with the approved intent, using the actual exposure window and population. Start with what shipped, who could use it, what changed concurrently and which events are reliable. A live service and a published announcement establish availability, not user value.

1. Compare baseline, target and observed result with consistent definitions. Check segment, time since exposure, lagging outcomes, missing data, and who did not receive the change. Pair quantitative observations with relevant feedback, support and known issue evidence.
2. Diagnose the size of the gap. A shortfall may be reach, activation, usability, an invalid assumption about value, or a measurement defect. Separate observations from competing explanations. Do not attribute all movement to the launch without a design that supports it.
3. Decide whether to keep, widen, change, reverse, or run a better test. For each recommendation name the evidence, downside, owner and next check. Open operational issues go to Deploy; causal technical issues go to Debug; product changes go back to requirements or discovery.
4. Record what the team learned and what would change the roadmap. Separate product learning from a team retrospective about the delivery process. Keep commitments visible; don't rewrite the original target to make the launch look successful.
